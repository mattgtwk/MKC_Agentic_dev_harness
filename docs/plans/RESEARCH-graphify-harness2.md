# Park graphify, borrow harness2's evidence rule

Graphify (graphify.com) is the commercial home of Graphify Labs (YC S26). The company sells a hosted "code knowledge graph for agents" built on an open-source engine, the PyPI package `graphifyy`, which is very popular, changes very fast and is still pre-1.0. The kit should **not** ship it in `harness/`. The kit should **name it as an upgrade path with a trigger** and give the person a **CLI-only, code-only, gitignored** recipe for the cases where it pays: large or inherited codebases, and corpora of papers or media. The reason is simple. Graphify's default install writes always-on text into `AGENTS.md` and `CLAUDE.md`, adds vendor PreToolUse hooks, installs a skill that is not in `skills-lock.json`, and adds git hooks. Each of those crosses a line the kit enforces. Meanwhile the independent evidence finds **no token or accuracy win over grep on repositories up to 25k nodes**, which is where a kit-bootstrapped repo spends most of its life. Google Research's harness2 is a different kind of thing. It is a research framework that **automatically optimises** a coding agent's harness through rollouts and judging, where the kit **governs** a harness that people change. Its machinery does not fit a one-task, human-approved repo. It reaches the kit's own design conclusions independently, though, and it has one idea worth taking: **a lesson is not promoted without named evidence**, and when the cause was not isolated the lesson is marked "confounded". The changes that follow from both tools are about five sentences of documentation and skill text. Neither tool justifies a script change. While checking the seams I confirmed one defect already in the kit, logged as BACKLOG: the `skills-lock` check reports "pinned" after testing only that the lock file exists.

## Graphify is an open-core product: 133k stars on a pre-1.0, Apache-2.0 engine

Graphify is live and first-party. graphify.com describes it as "the code knowledge graph for agents": a graph the assistant traces instead of grepping, with "no embeddings", and answers returned as graph paths with file:line citations ([graphify.com](https://graphify.com/)). The machine-readable index names the maker as **Graphify Labs, a Y Combinator S26 company, maintained by Safi Shamsi** ([llms-full.txt](https://graphify.com/llms-full.txt)). The old `safishamsi/graphify` repository now redirects to `Graphify-Labs/graphify`, whose homepage field is graphify.com. The free local engine and the paid hosted service are therefore one project in an open-core arrangement ([GitHub](https://github.com/Graphify-Labs/graphify)). The name is crowded. **graphify.net redirects to graaph.org**, a fan site that says it is "not affiliated with ... Graphify Labs" and points its install section at a different package ([graaph.org](https://graaph.org/)). The real package is **`graphifyy` with two y's**, and no PyPI package called `graphify` exists, so `uvx graphify` fails ([llms-full.txt](https://graphify.com/llms-full.txt)).

**What it does.** The engine parses code locally with tree-sitter for about 40 languages, PowerShell included. It needs no model call for code, and "nothing leaves your machine" ([README](https://github.com/Graphify-Labs/graphify/blob/v8/README.md)). Docs, PDFs and images get a semantic LLM pass. Inside the `/graphify` skill, that pass is run by the **host agent's own subagents**, or by Gemini when a Gemini key is set. Headless `graphify extract` instead auto-detects eight backends, and `GRAPHIFY_BACKEND=none` turns all of them off ([skill.md](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/skill.md); [README](https://github.com/Graphify-Labs/graphify/blob/v8/README.md)). Output goes to `graphify-out/` as `graph.json`, `GRAPH_REPORT.md` and `graph.html`. Edges are tagged EXTRACTED, INFERRED or AMBIGUOUS. The CLI offers `query`, `path`, `explain`, `update` (AST-only, no API cost), `watch`, `merge-graphs` and `prs`. There is an optional stdio MCP server, `graphify-mcp`, with about ten tools, among them `query_graph`, `shortest_path` and `get_pr_impact` ([serve.py](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/serve.py)). Exports cover Neo4j, FalkorDB, GraphML, Obsidian, SVG and Mermaid. "Differential verification" commands (`verify-edit`, `verify-plan`, `gate`) call Z3, CBMC and JBMC ([llms-full.txt](https://graphify.com/llms-full.txt)).

**Pricing and licence.** The engine was MIT until **2026-07-22, when it was relicensed to Apache-2.0**. The MIT text is kept as `LICENSE-MIT`, and write-ups that still say "MIT" are stale ([LICENSE commits](https://github.com/Graphify-Labs/graphify/commits/v8/LICENSE)). Hosted Graphify Cloud has four tiers ([llms-full.txt](https://graphify.com/llms-full.txt)):

| Tier | Price | What you get |
|---|---|---|
| Free | $0 | 3 repos, 25,000 nodes per repo, 10 push builds per day |
| Pro | $15 a month | Unlimited repos |
| Teams | $29 per seat a month | Minimum 2 seats |
| Enterprise | Custom | Self-hosted, SSO/SAML |

The hosted MCP endpoint at api.graphify.com/mcp uses OAuth. SOC 2 Type II is "in progress" and has no report yet ([llms-full.txt](https://graphify.com/llms-full.txt)).

**Maturity.** The repository was created on **2026-04-03**. On 2026-10-23 it had **132,931 stars, 12,721 forks and 1,602 open issues plus pull requests**. PyPI shows **262 releases**, the latest **0.9.94 on 2026-10-22**, with no GitHub Releases at all ([GitHub API](https://api.github.com/repos/Graphify-Labs/graphify); [PyPI](https://pypi.org/pypi/graphifyy/json)). That pace demands a pinned version in any recipe. The headline claim of "71.5x fewer tokens" comes from a 52-file mixed corpus of code, papers and images, and the project's own table gives **about 1x on the 6-file httpx repo** ([how-it-works.md](https://github.com/Graphify-Labs/graphify/blob/v8/docs/how-it-works.md)). One independent Python-only test measured 7.3x ([horadecodar](https://horadecodar.com.br/?p=47045)). Open issue #985 reports that plain Claude Code gave similar or better answers at the same or lower cost on a 10,202-node graph. A second user on a .NET monorepo found a graph-only agent cost **1.6 to 1.9 times more** ([issue #985](https://github.com/Graphify-Labs/graphify/issues/985)). There is also a long tail of open Windows bugs. Two matter on this machine: **#2989, where `hook install` writes a machine-specific interpreter path into tracked `.githooks` files**, and #2856, where a username with a space breaks query and update ([issues](https://github.com/Graphify-Labs/graphify/issues?q=windows+in%3Atitle)).

## Grep wins below 25k nodes, so the graph's case is narrow

The question for the kit is whether a graph helps the agents a bootstrapped repo actually runs, which are Opus- and Sonnet-class models on a repo that grows story by story. The one controlled independent benchmark says it does not. Across three small repos and one 25k-node repo, a code-graph MCP "cost more than Read/Grep in all three settings". On the large repo with Sonnet, grep was cheaper on 11 of 12 questions. The only accuracy gain was on structural questions with **Haiku** (12/12 against 8/12), and it did not appear with Sonnet. An earlier apparent saving disappeared once the author found that a CLAUDE.md had been loaded into every arm ([nefayran/code-graph-vs-grep](https://github.com/nefayran/code-graph-vs-grep)). That confound matters here. A repo with a good always-loaded map, which is exactly what the kit produces, shrinks the graph's marginal value. Anthropic's own position is that Claude Code's just-in-time grep and glob "bypass the issues of stale indexing and complex syntax trees" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

Graphs do win on a real niche. CodeCompass found **99.4% completion on hidden-dependency tasks with a graph MCP, against 76.2% for vanilla agents**. It also found that **58% of graph-enabled trials made zero graph calls** unless the agents were prompted to use the tool ([arXiv 2602.20048](https://arxiv.org/abs/2602.20048)). The nefayran benchmark found the same under-use, with 2 of 12 default runs calling the graph ([nefayran](https://github.com/nefayran/code-graph-vs-grep)). This explains graphify's install design. It pushes always-on routing text and PreToolUse "graph before grep" nudges because without them agents ignore the graph. Those nudges are exactly the part the kit refuses. Graphify's own code benchmark is n=6 on ERPNext: **82.0% key-fact coverage against 70.8% for grep/read**, at about 140K tokens per query ([BENCHMARKS.md](https://github.com/Graphify-Labs/graphify/blob/v8/BENCHMARKS.md)). A hands-on review of a roughly 2,000-line Swift app found the build slow and token-heavy and the graph missing real edges ([kofler.info](https://kofler.info/?p=9561)). The honest picture is that graphify earns its place on **large or inherited codebases, multi-hop impact questions, and heterogeneous corpora such as papers, PDFs and video**. That is a project-specific trigger, which is what the kit's upgrade-path list exists for.

## Graphify's installer collides with five kit invariants

Read from source at 0.9.94, graphify's integration is a set of **unprompted writes**. The bare `graphify install` copies a skill to `~/.claude/skills/graphify/` and **appends a `# graphify` block to the user's global `~/.claude/CLAUDE.md`**. `graphify claude install` writes a `## graphify` section into the project `CLAUDE.md` and **adds PreToolUse hooks on `Bash|Grep` and `Read|Glob` to `.claude/settings.json`**. A `--strict` option blocks the first raw file read of each session until a `graphify query` has run ([install.py](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/install.py)). The injected rule tells the agent to run `graphify query` "before your first grep, search or source-file read" and to copy that rule into every subagent prompt ([always_on/claude-md.md](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/always_on/claude-md.md)). Before issue #3435 was closed on 2026-10-12, that nudge had no session cap and was measured at **8,348 injections, about 651k tokens, in one project** ([#3435](https://github.com/Graphify-Labs/graphify/issues/3435)).

Each write lands on a kit guarantee:

| Graphify write | Kit guarantee it hits | Where the guarantee lives |
|---|---|---|
| A `## graphify` section in the project `CLAUDE.md` | `adapter-thin` fails, because `CLAUDE.md` must contain only `@./AGENTS.md` | [harness/AGENTS.md](../../harness/AGENTS.md) §2 |
| An always-on section in `AGENTS.md` | It costs bytes on every turn against the 24 KB and 32 KB caps, and if it lands in Part A it is a rule with no "Enforced by:" line | [harness/docs/HARNESS.md](../../harness/docs/HARNESS.md) "Token budget" |
| PreToolUse hooks | The kit ships no vendor hooks, and `--strict` would fight `harness-open`, which starts by reading files | HARNESS.md layer 4 |
| A project skill in `.agents/skills/graphify/` | It bypasses `skills-lock.json`, and the lint would not notice (see the BACKLOG below) | lint check `skills-lock` |
| Git rebuild hooks | `hooks.py` respects `core.hooksPath` ([hooks.py](https://github.com/Graphify-Labs/graphify/blob/v8/graphify/hooks.py)), and the kit arms `core.hooksPath .githooks` ([BOOTSTRAP.md](../../BOOTSTRAP.md) step 6). So `graphify hook install` would write new post-commit and post-checkout scripts into the **tracked** `.githooks/` folder, which is tooling under `TOOLING_RE`, and on Windows those scripts carry a machine-specific interpreter path (#2989) | `TOOLING_RE` in [harness_lint.py](../../harness/scripts/harness_lint.py) |

The hooks row resolves a question one research note left open. That note guessed the hooks would silently never fire. The source shows the opposite: they would fire and dirty a tooling directory. Upstream also recommends **committing `graphify-out/`** ([team-workflows](https://docs.graphify.com/guides/team-workflows)). In a kit repo that is a trap. `NOT_SOURCE_RE` in [harness_lint.py](../../harness/scripts/harness_lint.py) does not exclude `graphify-out/`, so `graph.json` and `graph.html` count as product files for `one-kind`. `SKIP` in [prepush_check.py](../../harness/scripts/prepush_check.py) excludes `.json` but not `.html`, so a regenerated `graph.html` draws surface refusals on push. The fix is a `.gitignore` line, not a regex change.

None of these collisions is necessary. The CLI works without any of the installer's instruction-file or hook writes. `uv tool install graphifyy`, then a code-only build with `GRAPHIFY_BACKEND=none` and `graphify query` on demand, touches only `graphify-out/` and a query log, which `GRAPHIFY_QUERY_LOG_DISABLE=1` turns off ([README](https://github.com/Graphify-Labs/graphify/blob/v8/README.md)). I derived that path from the docs and did not run it. uv is already in the BOOTSTRAP step 0 table, so the toolchain cost is close to zero.

## Harness2 optimises harnesses the kit governs by hand

Harness² is real, public and very new. Google Cloud AI Research and Northwestern describe it as "a plug-and-play framework for recursive agent harnessing in an open world". It **rewrites eight harness components automatically**: system prompt, guardrails, memory, tool guidance, subagents, skills, scripts and plugins. It does this through a contrastive Propose–Probe–Compose step that compares rollouts "without ground-truth feedback". It then keeps a per-domain library of adopted harnesses and evidence-backed lessons ([README](https://github.com/google-research/harness2/blob/main/README.md); [arXiv 2610.14224](https://arxiv.org/abs/2610.14224)). It reports gains of **up to 11.5 points on WorkBuddy-Bench, 4.5 on JobBench and 11.8 percentage points on LAB** from a single step ([README](https://github.com/google-research/harness2/blob/main/README.md)). The project site's own figures need checking against the paper before anyone quotes them. As software it is a research code drop. Apache-2.0, "not an officially supported Google product", **3 commits on `main`, no tags, zero merged pull requests, and 17,991 stars** as of 2026-10-23 ([GitHub API](https://api.github.com/repos/google-research/harness2)). It needs Linux, Python 3.12, Vertex credentials and Docker. **Claude Code is not a supported executor**: PR #125 was closed unmerged on 2026-10-21 ([PR #125](https://github.com/google-research/harness2/pull/125)). It runs Codex "with its sandbox disabled", and in one validation run a rollout downloaded its own grading rubric ([EXPERIMENTS.md](https://github.com/google-research/harness2/blob/main/docs/EXPERIMENTS.md)).

The fit question has a clear answer. Propose–Probe–Compose needs repeatable tasks, **R = 4k rollouts per task** and a judge ([ledger.py](https://github.com/google-research/harness2/blob/main/harness2/core/ledger.py)). A development repo has one real task, done once, and its plans stop for human approval in `harness-plan`. You cannot even point harness2 at your own repo yet, because `--bench local` is still a proposal ([issue #5](https://github.com/google-research/harness2/issues/5)). What makes harness2 useful to the kit is that it reached the kit's conclusions independently. It caps always-on text because "AGENTS.md is injected whole into EVERY turn" ([codex.py](https://github.com/google-research/harness2/blob/main/harness2/substrate/codex.py)). It routes domain knowledge to triggered skills. It carries the full record instead of a summary. And it treats `KEEP_BASE` as a valid answer, because "adaptation that the evidence does not argue for is a regression" ([prompts.py](https://github.com/google-research/harness2/blob/main/harness2/core/prompts.py)).

The idea worth taking is its **lesson discipline**. A library entry is refused unless it has a non-empty `cue`, `lesson` and `evidence` ([library.py](https://github.com/google-research/harness2/blob/main/harness2/core/library.py)). The reflection step labels each changed component `helped`, `hurt`, `no observed effect` or `confounded`, and it prefers `confounded` when the edits were not isolated, because "an invented attribution poisons the library for every later task" ([prompts.py](https://github.com/google-research/harness2/blob/main/harness2/core/prompts.py)). The kit's `harness-close` step 6 already has the `NO_ENTRY` equivalent (`- none: <reason>`), and the push gate checks that each named owner file changed ([harness-close](../../harness/.agents/skills/harness-close/SKILL.md)). But step 6 never asks a promoted lesson **what evidence it rests on**. That gap is exactly how a plausible but untested rule gets into Part A. The one genuine disagreement concerns hooks. harness2 calls in-loop plugins "the only lever that can enforce something the model cannot skip" ([opencode.py](https://github.com/google-research/harness2/blob/main/harness2/substrate/opencode.py)). The kit says git and CI are the only lever every agent shares. Both are right about different failures: a turn-time hook catches a problem at the turn, and a git hook catches it at the commit. The kit's stance holds because CI is binding, but the trade-off deserves one written sentence.

## Five sentences of text cover everything worth doing now

**Recommendation.** Do not add graphify, its skill, its hooks or a `graphify-out/` convention to `harness/`. Do not adopt any harness2 machinery. Make the text-only changes below, in rank order, as one docs PR. Under the user's rule 1, its declared surface is `harness/docs/HARNESS.md`, `BOOTSTRAP.md`, `harness/.agents/skills/harness-close/SKILL.md` and `harness/docs/memory/README.md`. None of these is tooling under `TOOLING_RE`, so the PR is a single kind. Item 3 changes what a close requires. Whether that counts as a "rule change" needing a bump of the `harness-constitution v1.2.0` line is **a decision for Matt, not something I have settled**. Kit `AGENTS.md` requires a bump "for any rule change", and step 6 is skill text, not Part A. After the edits, run the three selftests named in the kit's [AGENTS.md](../../AGENTS.md).

## Conclusion

The two tools together say something about where the kit's value sits. Graphify's own installer shows that a code graph only changes agent behaviour when it is forced into every turn, through always-on routing text and pre-tool hooks. The independent benchmarks show that agents ignore the graph without that pressure. So graphify's value depends on exactly the vendor-side, every-turn machinery the kit rejects on principle. What the kit can offer instead is a dated, checkable map that agents read once at `harness-open`. And the one benchmark that controlled for an always-loaded document found that such a document erased the graph's apparent savings. On small and medium repos the kit's curated map is already the competitive answer, and graphify becomes a per-project tool for the large or inherited codebase, not part of the template.

harness2 confirms the kit's design from the opposite direction, and it exposes the kit's weakest link. The kit enforces that a lesson reaches its owner file, but not that the lesson is true. A rule promoted from one confounded session is the kind of failure the user's PR #191 record describes: a plausible claim that nothing enforces. Asking every promoted lesson to name its evidence costs one sentence and closes that gap. The pinning gap in B1 is the same failure, already present in the lint.
