## Context

Matt asked for four things:
1. Whether and how to integrate graphify.com and google-research/harness2. The research is in `reports/Graphify harness integration.md`.
2. Always compare what each offers against what the kit already does. That comparison is in the report and now in memory as a standing preference.
3. Make the new Interfaces Design Bible (`docs/Interfaces Design Bible.md`, untracked, 61 KB, by Angus Hervey, cleared to publish) a skill that harness users can benefit from.
4. A change log in this repo that an existing harness user can point their agent at, so it selectively brings their harness up to date.

Findings that shape the plan:
- **Graphify.** Don't ship it. Its installer writes into the adapters, `.claude/settings.json` hooks and the tracked `.githooks/`, which breaks `adapter-thin`, the no-vendor-hooks rule and `skills-lock`. Independent benchmarks find no win over grep up to 25k nodes. It becomes an upgrade path with a trigger and a CLI-only recipe.
- **harness2.** It is a rollout-and-judge optimiser and doesn't fit the kit. Take its rule that a lesson needs evidence, and that a cause which was not isolated is recorded as confounded.
- **Bible vs kit.** The kit has nothing on UI craft, so this is a real gap. Compared with `jakubkrehel/skills`: those are review commands (`/better-ui` and the rest), while the bible is the consolidated rules, numbers and source disagreements. Ship the bible as the reference skill and name Krehel's skills as an optional companion.
- **Upgrades today.** HARNESS.md:68-70 says "re-copy `harness/` over the repo, keep Part B". That is all-or-nothing, with no record of what changed. A kit `CHANGELOG.md` was cut in v1.0.0 review (`docs/plans/PLAN-harness-kit-2610031330.md:91`). Matt's request is now the measured need.

## C. UPGRADE.md (selective upgrade recipe)

- **Location.** The kit root, as a sibling of `BOOTSTRAP.md`: one recipe to stand up a harness, one to bring it current. The bootstrapped `AGENTS.md:3` already carries `harness-constitution vX.Y.Z (kit: github.com/mattgtwk/...)`, so a user tells their agent: "follow UPGRADE.md from the kit named in AGENTS.md line 3".
- **Header procedure.**
  1. Read your version line.
  2. Apply every entry newer than it, oldest first.
  3. Edit only the named Part A bullets, never Part B or your records.
  4. Skip an entry marked *optional* unless its condition holds.
  5. Run each entry's Check, then the lint.
  6. Bump the version line last.
  7. Record what was applied or skipped in the session log.
- **Entry shape**, newest first:
  ```
  ## v1.3.0 (2026-10-xx)
  - <change>: Kind rule|skill|doc|script|optional (<condition>). Why: <one line>.
    Apply: re-copy kit `harness/<path>` | replace the bullet starting "<text>" | run `<cmd>`.
  Check: <command and expected line>
  ```
- **Backfill.** Write v1.1.0 (`4e81024`) and v1.2.0 (`9f59f10`) from `git show --stat`, plus v1.0.0 as the baseline: "bootstrap instead". BOOTSTRAP-only commits are not listed, because existing users have already bootstrapped.
